# Decision Log

Format: `D-NNN — topic — decision — rationale — date`

- **D-001 — SR data source** — The dedicated server's result data (incidents, contacts) is authoritative. Client telemetry from the desktop app only adds to it (e.g. off-tracks). — The client can be tampered with, the server can't. — 2026-11-03
- **D-002 — Desktop app requirement** — The app is required to race, but a missing app or heartbeat does **not** kick or DQ the player. Repeat offenses lead to a penalty (exact penalty TBD). — Keeps the barrier low for one-off glitches while still discouraging people from disabling the app. — 2026-11-03
- **D-003 — Identity** — Login via Steam OpenID. The SteamID is the key that links a player to their RRE driver on the server. — RRE runs on Steam, so linking needs no extra steps. — 2026-11-03
- **D-004 — Split allocation** — Split count = ceil(players / grid max), with players spread evenly. **SR outweighs ELO** in the split ranking. — Fast but unsafe drivers must not end up in the splits of slow but safe drivers. — 2026-11-03

- **D-005 — Split ranking formula** — A weighted score: normalized SR weighted above normalized ELO (e.g. 0.7/0.3, tunable). No SR bands or hard gates. — With a small player base early on, bands would fragment players too much. — 2026-11-03
- **D-006 — No-app penalty** (refines D-002) — Repeat offenses only flag the player for manual admin review. There is no automatic penalty. — 2026-11-03
- **D-007 — ELO model** — Multiplayer pairwise ELO: each finish is evaluated as duels against every other driver in the split. — Proven (LFM/iRacing-style) and simple. — 2026-11-03
- **D-008 — DNF / failures** — A player DNF or disconnect counts as a classified last place. A server crash voids that split's results, with no ELO/SR change. — Stops rage-quit exploits while staying fair when the infrastructure fails. — 2026-11-03
- **D-009 — Minimum players** — A race needs at least 2 registrations. With fewer, it is cancelled and the player is notified. — The platform should feel alive while the player base is small. — 2026-11-03
- **D-010 — Ranked flag** — Each race has a ranked/unranked flag in the CMS. Practice is always unranked. — 2026-11-03
- **D-011 — Rating scope** — One global ELO + SR for now. Store every rating change tagged with sim and car class so per-sim (or per-class) ratings can be recomputed later. — Keeps the pool unified now and the option open later. — 2026-11-03
- **D-012 — SR inputs** — Counts car contact (server), off-tracks / track limits (client + server) and spins / loss of control (client, from shared memory). Server-issued penalties/DQs do **not** feed SR. Weights TBD. — 2026-11-03
- **D-013 — Contact blame** — No-fault: both cars in a contact take the same SR hit. — Simple and hard to game, and it evens out over many races. — 2026-11-03
- **D-014 — Newcomers** — Start at ELO 1500 and a below-median SR. A provisional higher K-factor applies for the first ~5 races. — 2026-11-03
- **D-015 — Unregister / no-show** — Unregistering is allowed until splits are built. A no-show after that = DNF, i.e. a classified last place (D-008) with an ELO loss. — Keeps splits full and makes registering mean something. — 2026-11-03
- **D-016 — Race timing** — Registration runs T-30 to T-5. Splits are built at T-5, servers spin up and players get a 5-min join window. The race session starts at T-0. — 2026-11-03
- **D-017 — No-show appeals** — A no-show always counts as DNF. Technical failures are handled through manual admin appeal. — 2026-11-03
- **D-018 — Session structure** — Free practice (5 min, during the T-5 join window), then qualifying, then the race. Qualifying and race lengths are set per race in the CMS. — 2026-11-03
- **D-019 — Hosting** — The RRE dedicated server **must** run under Wine in Linux containers, because budget rules out Windows. Two spikes are needed: (a) Wine viability, and (b) getting around RRE's limit of 5 servers per instance by running multiple containers. — 2026-11-03
- **D-020 — Frontends** — A public website (driver profiles, results, leaderboards) plus a Tauri desktop app. Both share the UI code. — Shareable profiles drive growth, and Tauri lets us reuse the web UI. — 2026-11-03
- **D-021 — DLC ownership** — The desktop app checks ownership of the required car and track at registration and blocks registration if the player doesn't own them. Feasibility is spike S-5. — 2026-11-03
- **D-022 — Business model** — Free at launch, monetization decided later. — Grow the player base first. — 2026-11-03
- **D-023 — Region** — Game servers are EU-only at launch. API and web run on Cloudflare (global edge). The orchestrator and scheduling must be **region-aware** (each server host carries a region tag) so US/Asia hosts can be added later. — 2026-11-03
- **D-024 — Admin tooling** — Payload CMS handles race scheduling, the player flag/appeals queue (D-006, D-017), player bans and manual race voids (D-008). A live split/server dashboard is a **separate app**, not part of Payload. — 2026-11-03
- **D-025 — Cloud architecture** — Everything except the game servers runs on Cloudflare: Workers for API, web, competition service and Payload; D1 for auth-related data; Neon Postgres via Hyperdrive for everything else (including Payload); R2 for storage (result JSONs, replays); Durable Objects for realtime (live client events, split state). — 2026-11-03
- **D-026 — Orchestrator link** — The cloud pushes commands (create/stop splits) to the bare-metal orchestrator over **Workers VPC**, so no public inbound port is needed. Each region host gets its own VPC service (D-023). The orchestrator sends results back to the API. — 2026-11-03
- **D-027 — First milestone** — Infra spikes only (S-1..S-6). Product build planning starts once they're resolved. — The Wine/RRE feasibility question decides whether the whole project is viable. — 2026-11-03
- **D-028 — Orchestrator link (refines D-026)** — One Workers VPC *Service* binding per host. Adding a host means a config change and a redeploy, which is fine while there's a single box. The orchestrator authenticates at the app level with HMAC-signed requests, because Workers VPC doesn't authenticate requests at the origin. The return path uses an Access service token to a Worker. Plain Tunnel + Access is the fallback if the beta becomes a problem. See research/workers-vpc.md. — 2026-11-03
- **D-029 — Server image** — Production uses a **prebuilt Docker image with the RRE dedicated server baked in at build time**. No SteamCMD install happens at container start. — Fast, reproducible spin-up of splits at T-5. — 2026-11-03
- **D-030 — Server image base** — Build our prebuilt image (D-029) on the approach from procinger/r3e-oci: GE-Proton Wine with a patched httpapi.dll, a .NET 4.8 prefix template, Xvfb, a TTY and an nginx proxy in front of the loopback-only admin. Fork or pin it, and move the SteamCMD install to build time. **Anonymous download works**, so no build account is needed. — S-1 passed. — 2026-11-03
- **D-031 — Instance scaling** — One container per server instance, with **one unique registration secret per container**. Each (IP, secret) pair gets its own quota of 5. The orchestrator owns secret generation and registers each container via `/dedi/register` on first boot. Running more than 5 live servers is still to be confirmed (S-2b). — 2026-11-03
- **D-032 — Server control** — The orchestrator drives each server through its local REST API (`/dedi`, `/session`, `/result`, `/chat`, `/ban`) over loopback inside the container. No UI automation. — Found in S-3. — 2026-11-03
- **D-033 — Server networking** — **One live server per container** (the manager's port allocation is broken under Wine, see S-2b). On the production box, test first whether host-port remapping works for listing and joining. If it doesn't, fall back to one public IP per container (macvlan/ipvlan). — 2026-11-03
- **D-034 — Health = active polling, never trust return codes** — RRE servers are known to crash silently, and this was observed in the spike: `/dedi/start` returned `IsStarted: true` for instances that were crash-looping. The orchestrator treats a server as healthy only if `GET /dedi` reports `ProcessState.Running == true` **and** its state progresses (`SessionTimeLeft` / `TimeLeft` change, players count plausible), **and** the `DedicatedServer.exe` PID in the container is stable. Poll every few seconds. When state is stale or the PID changes, mark the split as crashed, which voids the results (D-008). Never rely on start responses or exit codes alone. — 2026-11-03

- **D-035 — ELO delta mechanics** — Average the pairwise duels into one delta: `ΔR = K · (S_avg − E_avg)`, where `S_avg = (n − pos) / (n − 1)` and `E_avg` is the mean of the pairwise expectations. A 20-car split swings ratings no more than a 2-car split, and the split stays zero-sum. — Summing the duels would make field size the dominant variable instead of driving. — 2026-11-03
- **D-036 — Split score normalization** (refines D-005) — Rank both ratings as percentiles within the **registered pool**, then weight: `score = 0.7 · pct(SR) + 0.3 · pct(ELO)`. — D-005's 0.7/0.3 only means something on a common scale; raw SR (~0–100) against raw ELO (~1500) makes SR about 12% of the score. Percentiles also make splits evenly sized by construction. Trade-off accepted: your placement depends on who signs up. — 2026-11-03
- **D-037 — SR update model** — Incidents-per-corner (CPI), rate-based: `ΔSR = k · (target − cpi) · corners`, with `cpi = incidentPoints / corners` and `corners = laps × cornersPerLap`. — A 5-minute sprint and a 30-minute race are judged on rate, so race length doesn't decide who gains. — 2026-11-03
- **D-038 — SR parameters v0** (tunable) — SR is a 0–100 float starting at 50 (D-014). Weights: contact 2, loss of control 2, off-track 1. Neutral `target = 0.08` points/corner, `k = 0.5`, per-race clamp `+3 … −6`. — Softened from the first draft at the user's request. Cost accepted: with a 0.08 target an average race is SR-positive, so the population drifts toward the ceiling (see open-questions). — 2026-11-03
- **D-039 — SR incident source** (narrows D-012) — SR uses only the dedicated server's result JSON incidents, scored with our own weights (D-038) rather than the server's `Points`. The desktop app reports no incidents; it is heartbeat/presence only. — Shared memory exposes aggregate counters (`incident_points`, `cut_track_warnings`), not discrete events, so client/server dedupe would have needed matching the data cannot support. The server is also the untamperable authority (D-001). — 2026-11-03
- **D-040 — Incomplete races and SR** — A DNF, disconnect or no-show leaves SR untouched; the classified last place in ELO (D-008, D-015, D-017) is the punishment. — No corners driven means no safety sample. Accepted consequence: a driver can crash and quit to dodge the SR hit; that is left to the admin flag/appeal queue (D-006, D-017) rather than an automatic rule. — 2026-11-03
- **D-041 — Server density and ports** (supersedes the one-server-per-container part of D-033) — One container/manager runs **up to 5 live servers**, the KW quota per (public IP, secret). Each instance takes a 3-port block: game UDP `port`, game TCP `port+1`, time UDP `port+2`. Ports are allocated monotonically from `60000` and reset on manager restart; they are not reused within a manager lifetime. The S-2b "one live server per container" result was a QEMU/CPU-starvation artifact, not a Wine bug. Plan capacity at **~0.17 core and ~110 MB per idle server** including shared manager/wineserver overhead. Because every manager starts allocating at `60000`, multiple containers on one host still need one IP per container (macvlan/ipvlan) or a base-port mechanism. — Evidence: `research/rre-dedicated-server.md` (S-2b re-run, real x86). — 2026-11-03
- **D-042 — Manager restart recovery** — Treat the manager's persisted server list as untrusted: on manager/container boot, delete every persisted server (`DELETE /dedi/{id}`) and recreate splits from the orchestrator's own state. Never start a persisted ID — it crashes the manager (`AccessViolationException` after unimplemented `httpapi.dll.HttpCancelHttpRequest`). Health checks must require PID stability plus session progress, not just `ProcessState.Running`, because the manager auto-restarts crashed game servers on the same port and `/dedi` is briefly stale during the restart. — 2026-11-03

- **D-043 — Base K** — `K = 32` on the D-035 formula. Within a split, near-equal duelists move about ±16 per race, so a 300-point climb takes roughly 19 races (~6 weeks at 3 races/week); the hard per-race ceiling is ±32. — Splits already keep fields near-equal, so the fast-moving duels are the ones that matter, and the provisional (D-044) absorbs newcomer convergence. — 2026-11-03
- **D-044 — Provisional K** (completes D-014) — Exactly 3× base (`K = 96`) for a player's **first 5 rated races**, then straight to base. Unranked races (D-010) don't consume the window. — Trivial to explain and matches D-014 literally. Accepted cost: a hard 3× step between race 5 and 6; a decay formula is the fallback if the cliff proves unfair in practice. In a 20-car split the field multiplier (D-045) stacks, so a newcomer's first race can move ±96. — 2026-11-03
- **D-045 — K scales with field size** — `K_eff = K · clamp(√((n−1)/4), 0.5, 2)`: a 2-car duel counts 0.5×, a 5-car split 1×, a 20-car split 2×. — A larger field is a better estimate of relative skill, so it should move ratings further; a coin-flip duel should barely move them. Keeps D-009's two-driver minimum alive instead of making small races meaningless. — 2026-11-03

- **D-046 — Database topology** (supersedes the D1 part of D-025) — **No D1.** Neon Postgres via Hyperdrive is the only database, holding identity, profiles, ratings, race definitions, results and rating history. Sessions are stateless JWTs, so no database read sits on the auth hot path, and account + profile creation is one transaction. — D-025 split auth into D1 on the assumption that auth needs a low-latency store; with JWTs there is no auth query to make fast, and a second store only adds a cross-store write (saga/outbox) plus a second backup. — 2026-11-03
- **D-047 — Registration and split building** — One Durable Object per race occurrence: `register()` is serialized (dedupe and capacity enforced there), and an alarm at T-5 builds the splits and writes the roster and split assignments to Postgres. — The DO puts serialization and the deadline in one place, with no advisory locks or cron race, and D-016 needs exactly one decision point at T-5. — 2026-11-03
- **D-048 — Result storage** — The result JSON goes to R2 unchanged, addressed by race/split/driver; the same payload is parsed into Postgres result, incident and rating-event rows, with every rating change tagged by sim and car class (D-011). — Keeping the raw file means a parser bug or a scoring change can be fixed by re-parsing, which is the whole point of D-011. — 2026-11-03
- **D-049 — Website data access** — The website reads everything through the API and never queries Postgres directly. — One authorization path and one schema boundary, and API responses are still cacheable at the edge. — 2026-11-03

- **D-050 — Provisioning** — Managers stay resident on the host and are recycled; at T-5 the cloud pushes create/start and each server comes up in seconds on the prebuilt image (D-029). Nothing waits on a cold container boot inside D-016's 5-minute window. — Pays the manager's resident footprint continuously but keeps the deadline path predictable. — 2026-11-03
- **D-051 — Cloud→orchestrator link failure** — Push at T-5 and retry with backoff until T-1; if it still fails, cancel the occurrence and notify the roster. The cloud stays the only authority over what runs. — Accepted risk: a short Workers VPC blip at the deadline voids a race players already committed to. Chosen over pre-pushing a `startAt` plan, which would let the host act on state the cloud hasn't confirmed. — 2026-11-03
- **D-052 — No-show scoring** (implements D-015) — Score each split from the **durable roster joined to the result file**: drivers present get their finish, any roster entry missing from the file is a classified last place, and a driver present but DNF uses the position in the result. — The result file never contains a player who didn't connect, so without the join a no-show would escape ELO entirely. The T-5 roster write (D-047) must therefore complete before scoring starts. — 2026-11-03
- **D-053 — Capacity** — Registration is hard-capped at `hostCapacity × gridMax`, enforced in the DO (D-047) and shown on the race page; registration closes when full. — With one EU box at launch, a cap makes the T-5 build unable to fail on capacity and tells players the limit before they commit, instead of splitting the field into ranked and unranked halves. — 2026-11-03

- **D-054 — Zero-finisher split** — If no roster driver connects, the split is voided like a server crash (D-008): no ELO, no SR, and an item in the admin queue. — Scoring everyone as last place is not zero-sum and would drain ratings for a race nobody drove; the void keeps D-052's roster rule intact. Accepted risk: a coordinated no-show escapes ELO, visible to admins who can act on it. — 2026-11-03
- **D-055 — One-driver split** — If exactly one roster driver connects, the split is voided, ratings unchanged, and the driver is notified with priority for the next race. — D-035's `S_avg = (n − pos)/(n − 1)` has no meaning at `n = 1`, and awarding a win would make farming empty splits the fastest way to gain ELO. — 2026-11-03
- **D-056 — Practice servers** — One always-on public practice server per region, unranked (D-010), whose track and cars mirror the next scheduled race; the orchestrator replaces it when that definition changes. — Keeps the platform from being empty six days a week, which is when new players look, at the cost of one of a manager's five slots (~0.17 core / 110 MB). This replaces the vision's "1 hour of free practice per race" wording. — 2026-11-03
- **D-057 — Voided race display** — Voided races (D-008, D-054, D-055) are hidden from public profiles and leaderboards entirely. — Clean profiles, with the accepted consequence that a driver who remembers racing that night sees nothing and may read it as a bug; the admin queue remains the record of what happened. — 2026-11-03

- **D-058 — Desktop app scope** (supersedes the background-service part of D-002) — The app has **no background service**. It is the launcher, the registration surface and the results viewer; presence comes from the dedicated server's player list (D-034), not from the client. "The app is required to race" now means you register and join through it — the per-split join password is issued to roster players only — and a driver who is not in the split is a no-show (D-015). — Once D-039 removed telemetry, a heartbeat could only attest that a process was open, which the server already knows better. Consequence: D-006's app-missing offence no longer exists, so that flag queue becomes admin-initiated only. — 2026-11-03
- **D-059 — Login** — Steam OpenID in the system browser with a loopback callback; the app exchanges the assertion for a JWT (D-046). The website uses the same flow (D-020). — Avoids embedded-webview Steam quirks and keeps one login path for both frontends, at the cost of a browser window opening beside the app. — 2026-11-03
- **D-060 — Ownership failure mode** (refines D-021) — Ownership known-missing blocks registration; ownership **unknown** (private profile, API unavailable) registers with a warning, and the server still enforces content at join. — Blocking on unknown would lock out the many Steam profiles that default to private, and turn our uncertainty into a missed race for the player. — 2026-11-03
- **D-061 — App updates** — Auto-update on launch, and the API rejects registration from clients below a minimum supported version, which the app surfaces as a blocking update prompt. — Prevents a split running mixed client behaviour, at the cost of a bad release blocking play until it is fixed. — 2026-11-03

- **D-062 — Ops dashboard is read-only** — The live dashboard shows splits, server health (D-034), players online, session phase and results landing, with **no write path** to the orchestrator. Actions are taken in Payload admin instead. — Keeps the operational view observational, so there is no second authenticated write surface facing the bare-metal host. Accepted cost: a disruptive driver is handled through Payload rather than from the live view. — 2026-11-03
- **D-063 — Admin roles** — Payload users with three roles: `admin` (everything), `race director` (kick, void, flag queue) and `viewer` (read-only), enforced in the API as well as in Payload's UI. — One identity system, with the authorization check repeated at the API so the UI is not the only gate. — 2026-11-03
- **D-064 — Race definition locking** — A race definition is editable until registration opens (T-30) and immutable for that occurrence afterwards; a mistake found later means cancelling the occurrence, not editing it. — Players register against a fixed layout, car list and length, and the practice server (D-056) can't disagree with what actually runs. — 2026-11-03
- **D-065 — Disputed race resolution** — When a dispute is upheld, re-score the split with the offending driver excluded and append new rating events, rather than voiding the split. Needs a per-split pre-race rating snapshot for a deterministic replay, with the raw result file in R2 (D-048) as the input. — Voiding (D-008) makes every other driver pay for one offender, and the event log from D-011/D-048 already makes replay feasible. — 2026-11-03

- **D-066 — Stack** — TypeScript everywhere, all of it on Cloudflare: Workers for every service, Durable Objects for per-race state (D-047), R2 for artifacts (D-048), Neon Postgres via Hyperdrive for data (D-046). The only machine we operate ourselves is the bare-metal game host. — One language end to end, and no servers to patch beyond the box that has to run Wine. — 2026-11-03
- **D-067 — API surface** — Public HTTP APIs are Hono apps on Workers, consumed through the Hono RPC client so the website, the desktop app and the ops dashboard are typed against the routes at build time. Calls between our own Workers use **service bindings**, never public HTTP. — RPC typing removes a hand-maintained client contract, and service bindings keep internal calls off the public edge. — 2026-11-03
- **D-068 — Data access** — Drizzle ORM for the domain schema, connecting with `pg` over Hyperdrive. — Hyperdrive pools TCP connections, so the Neon HTTP driver isn't the path; `pg` is. This also matches what any Postgres-backed admin framework will use. — 2026-11-03
- **D-069 — Frontends** — React on Vite, one UI shared by the public website (deployed as a Worker) and the Tauri app (D-020), with TanStack Router, Query and Form. — A single frontend build for both surfaces, and Query's cache semantics fit an API-only read path (D-049). — 2026-11-03

- **D-070 — Admin scope** (supersedes the admin-scope part of D-024, and relocates the actions in D-062/D-063) — Payload handles **race management only**: creating and scheduling races, eligible cars, track, session lengths and their media. Everything else — players, ratings, results, flags and appeals, bans, void/re-score, audit and live splits — lives in our own Hono API with Drizzle, with our own React/Vite admin UI. — Payload is good at content modelling and poor as a general application backend; one domain backend keeps a single auth system, a single audit trail and one place where rating-affecting actions happen. — 2026-11-03
- **D-071 — Authentication** (supersedes the hand-rolled-JWT part of D-046 and the "Payload users" part of D-063) — **Better Auth** on the API owns accounts and sessions. Steam remains the only identity (D-003, D-059), and `admin` / `race director` / `viewer` are Better Auth roles re-checked by the API (D-063). — One auth system for web, desktop and dashboard instead of one per frontend. Risk: Better Auth's social/generic OAuth providers speak OAuth2/OIDC while Steam is OpenID 2.0, so the Steam bridge has to be proven early (see open-questions). — 2026-11-03

- **D-072 — Race definitions ownership** — Payload owns race definitions in its own rows. The API reads them from the Payload Worker over a **Workers service binding** (HTTP only as a fallback), and the domain schema keeps no copy. D-064's lock is enforced on the Payload document at T-30; a locked definition is immutable by rule and the API treats it as such. — One source of truth for content, no sync path, and consistent with D-067's rule that our Workers talk over service bindings rather than public HTTP. — 2026-11-03
- **D-073 — Desktop session transport** — The website uses Better Auth's cookie; the Tauri app keeps a **bearer session token** from the loopback callback (D-059) and sends it on API calls. — Avoids cross-origin cookie constraints between the API origin and the Tauri webview, and Better Auth supports both carriers. — 2026-11-03
- **D-074 — Steam identity bridge** — Steam OpenID 2.0 is implemented as a **Better Auth provider plugin**, so accounts, sessions and the D-063 roles stay inside Better Auth's model. — One account model for web, desktop and dashboard. Because Better Auth's provider plugins are shaped around OAuth2/OIDC, this is the earliest technical risk to retire. — 2026-11-03
- **D-075 — Own the server image** — Our own multi-stage Dockerfile replaces the `procinger/r3e-oci` base: it compiles the patched `httpapi.dll` from the pinned Valve Wine revision, downloads GE-Proton, SteamCMD and Winetricks directly, and bakes the server and the .NET 4.8 prefix at build time. The MIT-licensed patch is carried with attribution in `infra/rre-server/THIRD-PARTY.md`. — Pinning only upstream inputs removes an opaque 8 GB third-party base and lets us patch or bump the runtime ourselves; the previous derivative image was verified, the new one needs its first build on a Docker host. — 2026-11-03

- **D-076 — Website rendering** (refines D-069) — The **website** renders server-side with TanStack Start on Workers, so driver profiles carry real HTML, OG tags and indexable content. The **Tauri app** keeps the client build of the same React components. — D-020 justified the public site as the growth engine through shareable profiles, and a pure SPA gives those links no preview and no search presence. Cost accepted: SSR data-loading exists only in the web app. — 2026-11-03
- **D-077 — Definition freeze** (refines D-072) — At T-30 the API reads the definition from Payload over the service binding and **freezes it into the occurrence row** as JSONB; splits and results reference `race_occurrences.id` with a real foreign key, and Payload is never consulted for that occurrence again. — Removes both failure modes D-072 left open: a Payload outage at T-5, and documents that can be duplicated or deleted out from under existing results. Payload remains the editor and the only source of truth *before* the lock. — 2026-11-03
- **D-078 — Payload authentication** (refines D-070/D-071) — Payload authenticates through a custom strategy that validates a **Better Auth** session, with admin, API and site on subdomains under one cookie scope. — Otherwise offboarding is a two-system checklist and a revoked race director keeps editing the schedule; Payload's own user collection would also duplicate the roles D-063 defines. — 2026-11-03
- **D-079 — Orchestrator link** (supersedes D-028) — **Cloudflare Tunnel plus an Access service token is the primary control path**, the GA mechanism already used for the reverse path. Host selection comes from data (KV or Postgres) rather than deploy-time bindings, and Workers VPC is an optional optimisation if it reaches GA. — The only control path to the product's only stateful machine should not depend on a beta with no SLA, no published latency and no GA date; the reverse path already speaks Access. Evidence: `research/workers-vpc.md`. — 2026-11-03
- **D-080 — Hyperdrive query caching is off entirely** — Every Hyperdrive configuration sets caching to `max_age = 0`, so no read is ever served from the edge cache; all queries reach Neon. Prepared-statement caching is a separate mechanism and stays on. — A driver must see the rating change from the race they just finished, so a cached row after a write is a correctness bug, not a latency trade-off; at this workload the result cache buys nothing worth that risk. — 2026-11-03

- **D-081 — Manager** — Replace the Windows `RRRE_Dedicated.exe` manager with the Rust port (`rrre-dedi-rs`), vendored at `infra/rre-server/manager` and pruned. The proprietary `DedicatedServer.exe` game payload stays and is embedded into the manager binary at build time from the SteamCMD install. — The port runs natively on Linux, so the .NET/WinForms manager, its HttpListener `Host: localhost:8088` quirk, its broken port allocation under Wine and the persisted-ID `AccessViolationException` (D-042) all disappear; the manager also stops costing a 30–90 s Wine boot inside the T-5 window. — 2026-11-05
- **D-082 — Private servers, no KW portal** — Servers do not register with the RaceRoom portal: no slave secret, no announcements, no content proxy, no quota. Splits are joined through the `rrre://` direct-join URI with the per-split password issued to roster players (D-058). — Removes the registration/announcement machinery (~2k lines), the per-container secret (D-031) and the one-public-IP-per-container requirement, because the orchestrator now supplies the host:port the client should use. **Blocking spike (S-7): direct join is unproven** — the client launched but never appeared on the server in the 2026-11-03 test. If S-7 fails, portal registration must come back. — 2026-11-05 — **Superseded by D-087 (S-7 failed).**
- **D-083 — One throwaway container per split** — Each split gets exactly one container running one manager and one game server on fixed 60000/60001/60002, auto-started at boot and destroyed once results are in. The manager is stateless (no SQLite, no scheduler, no persisted IDs, no track rotation) and keeps running after the game server exits so the orchestrator can read the final state and pull results. Supersedes D-041 (up to five live servers) and D-050 (resident, recycled managers). **Blocking spike (S-8): T-5 boot budget** — container start to joinable must fit inside the 5-minute window (pre-pulled image, baked Wine prefix). — 2026-11-05
- **D-084 — Result delivery is a push** — On `/slave/MultiplayerEventResult` the manager decrypts the payload, writes it locally and POSTs the raw JSON to the metarace ingest endpoint with a per-run bearer token and a result hash, retrying with backoff. It acknowledges the game server only after delivery, and exposes the stored file for manual recovery. — The game server's callback is the race-end signal (D-034) and R2 needs the raw file (D-048); pull-before-teardown would lose a result if the container died first. — 2026-11-05
- **D-085 — No live admin controls in v1** — Drop kick, forced session advance/restart, chat and MOTD from the manager, and with them the Windows named-pipe relay build. Sessions advance on their configured durations; abuse is handled by voiding the split (D-008). Deferred, not rejected: D-063's race-director kick needs the relay. — The relay adds a second Windows binary built with cargo-xwin to every container, and the 5-minute practice + timed sessions leave no routine need to advance a session manually. — 2026-11-05
- **D-086 — Manager control contract** — The manager exposes `GET /state`, `POST /stop` and result download behind a per-container bearer token; the game-server `/slave/*` callbacks stay unauthenticated (the game server sends no credentials) and are reachable only on the container network. `/state` includes the game-server PID, last-state-callback time, session progress and result-delivery timestamps, which is what D-034 needs to tell "running" from "crash-looping". Settings arrive at boot as a JSON environment value or file; there is no create/start REST dance. — One server per container makes ids, listing and CRUD meaningless; fail-fast boot removes the stale-state class of bugs. — 2026-11-05
- **D-087 — Portal registration is required** (supersedes D-082) — Every manager registers a slave with the RaceRoom portal at boot using a per-container secret (D-031), creates its settings there, takes the port allocation, and announces the server every interval; players join through the RRE **server browser** with the per-split password (D-058). S-7 failed: the `rrre://` direct URI did not put a client on the server, so the browser is the only join path. — Listing is the only proven way into a server. Consequences: the secret is a required runtime input, announcements and `POST /slave/GridRequest` return, and the orchestrator must keep the portal reachable at boot; metarace still receives the raw result JSON (D-084) and the manager also forwards the enriched result to the portal. **Verified by a browser join on 2026-11-05** (see `research/rre-rust-manager.md`). — 2026-11-05
- **D-088 — Bind the game server to IPv4** — The manager always passes `-ip <IPv4>` to `DedicatedServer.exe`: it auto-detects the container's primary IPv4 at boot and `METARACE_DEDI_IP` overrides it. — Without `-ip`, Wine binds IPv6 wildcard sockets (`/proc/net/udp6`/`tcp6`) while Docker and the gateway publish IPv4; the server lists but every join fails with "multiplayer session is closed". `-ip <container IPv4>` makes it bind `::ffff:<ip>` and the public path works. Evidence: `research/rre-rust-manager.md` §5. — 2026-11-05
- **D-089 — Announcement contract** — The announcement uses the portal's allocated port (no manual override unless the container mapping matches), and every `MpServerList` entry carries `Id` (the settings id), `Created` as an **ISO 8601 string**, the complete `GameSettings`, `ServerIp`, `Port`, `PortTimeCritical`, session/player fields and the compact `Settings` object; the compact object includes `SlaveId`. — A Unix-millisecond `Created` returns HTTP 400, and omitting `Id`/`SlaveId` makes the entry unusable even when the portal answers `true`; a forced port that differs from `GetPort` lists an unreachable address. Evidence: `research/rre-rust-manager.md` §2–4. — 2026-11-05
- **D-090 — Race definitions carry the full settings payload** — Race definitions produce the complete RRE `MultiplayerServerSettings` object (all `TrackLayouts` and sessions), not a minimal set of fields; the orchestrator sends it verbatim, changing only identity fields. — The portal rejects a trimmed payload with `Saving of Multiplayer settings failed (250)`; the full live settings succeeded. Consequence for the CMS schema: store the full template (or serialize it losslessly), and validate it against a real `SetSettings` call. — 2026-11-05
- **D-091 — One portal secret and settings create per container** (refines D-031/D-083) — Each container gets a fresh secret and creates its settings once; a secret is never reused across manager restarts. — `GetPort` advances with every settings create on a reused slave (`60000 → 60003 → 60006`), stale settings and ports accumulate, and the announced port can drift from the reachable one. A fresh secret keeps the mapping deterministic and the orphaned settings disposable. — 2026-11-05
