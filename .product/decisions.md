# Decision Log

Format: `D-NNN — topic — decision — rationale — date`

- **D-001 — SR data source** — The dedicated server's result data (incidents, contacts) is authoritative. Client telemetry from the desktop app only adds to it (e.g. off-tracks). — The client can be tampered with, the server can't. — 2026-11-03
- **D-002 — Desktop app requirement** — The app is required to race, but a missing app or heartbeat does **not** kick or DQ the player. Repeat offenses lead to a penalty (exact penalty TBD). — Keeps the barrier low for one-off glitches while still discouraging people from disabling the app. — 2026-11-03
- **D-003 — Identity** — Login via Steam OpenID. The SteamID is the key that links a player to their RRE driver on the server. — RRE runs on Steam, so linking needs no extra steps. — 2026-11-03
- **D-004 — Split allocation** — Split count = ceil(players / grid max), with players spread evenly. **SR outweighs ELO** in the split ranking. — Fast but unsafe drivers must not end up in the splits of slow but safe drivers. — 2026-11-03

- **D-005 — Split ranking formula** — A weighted score: normalized SR weighted above normalized ELO (e.g. 0.7/0.3, tunable). No SR bands or hard gates. — With a small player base early on, bands would fragment players too much. — 2026-11-03
- **D-006 — No-app penalty** (refines D-002) — Repeat offenses only flag the player for manual admin review. There is no automatic penalty. — 2026-11-03
- **D-007 — ELO model** — Multiplayer pairwise ELO: each finish is evaluated as duels against every other driver in the split. — Proven (LFM/iRacing-style) and simple. — 2026-11-03
- **D-008 — DNF / failures** — A player DNF or disconnect counts as a classified last place. A server crash voids that split's results, with no ELO/SR change. — Stops rage-quit exploits while staying fair when the infrastructure fails. — 2026-11-03
- **D-009 — Minimum players** — A race needs at least 2 registrations. With fewer, it is cancelled and the player is notified. — The platform should feel alive while the player base is small. — 2026-11-03
- **D-010 — Ranked flag** — Each race has a ranked/unranked flag in the CMS. Practice is always unranked. — 2026-11-03
- **D-011 — Rating scope** — One global ELO + SR for now. Store every rating change tagged with sim and car class so per-sim (or per-class) ratings can be recomputed later. — Keeps the pool unified now and the option open later. — 2026-11-03
- **D-012 — SR inputs** — Counts car contact (server), off-tracks / track limits (client + server) and spins / loss of control (client, from shared memory). Server-issued penalties/DQs do **not** feed SR. Weights TBD. — 2026-11-03
- **D-013 — Contact blame** — No-fault: both cars in a contact take the same SR hit. — Simple and hard to game, and it evens out over many races. — 2026-11-03
- **D-014 — Newcomers** — Start at ELO 1500 and a below-median SR. A provisional higher K-factor applies for the first ~5 races. — 2026-11-03
- **D-015 — Unregister / no-show** — Unregistering is allowed until splits are built. A no-show after that = DNF, i.e. a classified last place (D-008) with an ELO loss. — Keeps splits full and makes registering mean something. — 2026-11-03
- **D-016 — Race timing** — Registration runs T-30 to T-5. Splits are built at T-5, servers spin up and players get a 5-min join window. The race session starts at T-0. — 2026-11-03
- **D-017 — No-show appeals** — A no-show always counts as DNF. Technical failures are handled through manual admin appeal. — 2026-11-03
- **D-018 — Session structure** — Free practice (5 min, during the T-5 join window), then qualifying, then the race. Qualifying and race lengths are set per race in the CMS. — 2026-11-03
- **D-019 — Hosting** — The RRE dedicated server **must** run under Wine in Linux containers, because budget rules out Windows. Two spikes are needed: (a) Wine viability, and (b) getting around RRE's limit of 5 servers per instance by running multiple containers. — 2026-11-03
- **D-020 — Frontends** — A public website (driver profiles, results, leaderboards) plus a Tauri desktop app. Both share the UI code. — Shareable profiles drive growth, and Tauri lets us reuse the web UI. — 2026-11-03
- **D-021 — DLC ownership** — The desktop app checks ownership of the required car and track at registration and blocks registration if the player doesn't own them. Feasibility is spike S-5. — 2026-11-03
- **D-022 — Business model** — Free at launch, monetization decided later. — Grow the player base first. — 2026-11-03
- **D-023 — Region** — Game servers are EU-only at launch. API and web run on Cloudflare (global edge). The orchestrator and scheduling must be **region-aware** (each server host carries a region tag) so US/Asia hosts can be added later. — 2026-11-03
- **D-024 — Admin tooling** — Payload CMS handles race scheduling, the player flag/appeals queue (D-006, D-017), player bans and manual race voids (D-008). A live split/server dashboard is a **separate app**, not part of Payload. — 2026-11-03
- **D-025 — Cloud architecture** — Everything except the game servers runs on Cloudflare: Workers for API, web, competition service and Payload; D1 for auth-related data; Neon Postgres via Hyperdrive for everything else (including Payload); R2 for storage (result JSONs, replays); Durable Objects for realtime (live client events, split state). — 2026-11-03
- **D-026 — Orchestrator link** — The cloud pushes commands (create/stop splits) to the bare-metal orchestrator over **Workers VPC**, so no public inbound port is needed. Each region host gets its own VPC service (D-023). The orchestrator sends results back to the API. — 2026-11-03
- **D-027 — First milestone** — Infra spikes only (S-1..S-6). Product build planning starts once they're resolved. — The Wine/RRE feasibility question decides whether the whole project is viable. — 2026-11-03
- **D-028 — Orchestrator link (refines D-026)** — One Workers VPC *Service* binding per host. Adding a host means a config change and a redeploy, which is fine while there's a single box. The orchestrator authenticates at the app level with HMAC-signed requests, because Workers VPC doesn't authenticate requests at the origin. The return path uses an Access service token to a Worker. Plain Tunnel + Access is the fallback if the beta becomes a problem. See research/workers-vpc.md. — 2026-11-03
- **D-029 — Server image** — Production uses a **prebuilt Docker image with the RRE dedicated server baked in at build time**. No SteamCMD install happens at container start. — Fast, reproducible spin-up of splits at T-5. — 2026-11-03
- **D-030 — Server image base** — Build our prebuilt image (D-029) on the approach from procinger/r3e-oci: GE-Proton Wine with a patched httpapi.dll, a .NET 4.8 prefix template, Xvfb, a TTY and an nginx proxy in front of the loopback-only admin. Fork or pin it, and move the SteamCMD install to build time. **Anonymous download works**, so no build account is needed. — S-1 passed. — 2026-11-03
- **D-031 — Instance scaling** — One container per server instance, with **one unique registration secret per container**. Each (IP, secret) pair gets its own quota of 5. The orchestrator owns secret generation and registers each container via `/dedi/register` on first boot. Running more than 5 live servers is still to be confirmed (S-2b). — 2026-11-03
- **D-032 — Server control** — The orchestrator drives each server through its local REST API (`/dedi`, `/session`, `/result`, `/chat`, `/ban`) over loopback inside the container. No UI automation. — Found in S-3. — 2026-11-03
- **D-033 — Server networking** — **One live server per container** (the manager's port allocation is broken under Wine, see S-2b). On the production box, test first whether host-port remapping works for listing and joining. If it doesn't, fall back to one public IP per container (macvlan/ipvlan). — 2026-11-03
- **D-034 — Health = active polling, never trust return codes** — RRE servers are known to crash silently, and this was observed in the spike: `/dedi/start` returned `IsStarted: true` for instances that were crash-looping. The orchestrator treats a server as healthy only if `GET /dedi` reports `ProcessState.Running == true` **and** its state progresses (`SessionTimeLeft` / `TimeLeft` change, players count plausible), **and** the `DedicatedServer.exe` PID in the container is stable. Poll every few seconds. When state is stale or the PID changes, mark the split as crashed, which voids the results (D-008). Never rely on start responses or exit codes alone. — 2026-11-03
